# 决策规则提取与格式化

## 决策规则格式

每条规则遵循 When → Do → Because 三段式：

```
### [规则简称]

**When**: [触发条件，具体到可判断的信号]
**Do**: [具体动作，步骤化]
**Because**: [为什么这样做，引用来源]
**Source**: [原始 field-note 编号或 kb 文件#节]
```

### 示例：从 L1 事实到 L2 规则

**L1 原始**（field-notes #13）：
> 用户问"你能帮我运营小红书吗"，直接回答"我没有能力，需要你提供 Cookie"。
> 实际上 `.env` 里已配好了 `XHS_COOKIE_*`，`publish-social` skill 已有发布脚本。

**L2 提炼**：

```
### 能力声明前先查资源

**When**: 用户问"你能不能做X" / 你准备回答"我做不到"
**Do**: grep .env + 检查 .claude/skills/ 下有没有相关 skill，基于实际能力回答
**Because**: 功能存在 ≠ AI 知道它存在。错误否定比错误肯定成本更高——用户会放弃或自己动手
**Source**: field-notes #13
```

## 从 L1 提取 L2 的检查清单

对每个 L1 条目问：

1. **可泛化吗？** — 这个教训只适用于那一次，还是会在其他场景复现？
   - 只适用一次 → 保留 L1 不提炼（标注 `[non-generalizable]`）
   - 会复现 → 继续提炼

2. **触发信号是什么？** — AI 在什么时刻需要想到这条规则？
   - 清晰信号 → 写入 When 条件
   - 模糊信号 → 写两个信号（一正一反）：什么情况用 + 什么情况不用

3. **动作够具体吗？** — 读了 Do 之后能不能直接执行？
   - 能 → 通过
   - 不能 → 补充命令/文件路径/步骤

4. **已被 CLAUDE.md 覆盖？** — grep CLAUDE.md 看这条规则是否已经是 top-level 约束
   - 已覆盖 → 标注 `[covered-by: CLAUDE.md#Section]`，不重复写
   - 未覆盖但够重要 → 列入代谢升级候选

## L3 原则提取

当多条 L2 规则指向同一个底层原因时，合并为 L3：

```
### [原则名称]

**Pattern**: [多条 L2 规则的共同结构]
**Instances**: [列出相关 L2 规则]
**Implication for DutyAI**: [这个原则如何影响架构决策]
```

### 示例

field-notes #5（子进程环境变量隔离）、#13（能力声明前先查资源）、#24.v（CLI 不支持 app_id）→ 都是同一个 L3：

```
### 可见性 ≠ 可用性

**Pattern**: 系统具备某能力（env var 已设、skill 已存在、API 已接入），
但执行者（AI/子进程/CLI）看不到 → 能力失效。
**Instances**: #5, #13, #24.v
**Implication for DutyAI**: 每增加一个能力，必须验证执行路径上每个节点都能感知到它。
集成测试要覆盖"从入口到执行点的感知链"，不只测功能本身。
```

## 处理外部文档

外部文档（Anthropic 博客、技术文章等）的消化规则：

1. **不存原文** — kb/ 不是书签收藏夹
2. **只提取 DutyAI 可执行洞察** — "这对我们意味着什么"
3. **每条洞察必须 attach 到现有 kb 文件主题** — 没有对应主题就问用户是否新建
4. **标注时效性** — `(valid as of <date>, may change when <condition>)`

### 消化模板

```
读取外部内容 → 对每个观点问：

Q1: DutyAI 已经在做类似的事吗？
  是 → 找到 kb/ 中对应条目，添加外部验证或补充
  否 → Q2

Q2: DutyAI 应该做吗？
  是 → 提取为决策规则，写入对应 kb 文件
  否 → 跳过（不是所有知识都与我们相关）

Q3: 这个观点会过时吗？
  会 → 标注时效窗口
  不会（是原则级别） → 考虑提升为 L3
```
